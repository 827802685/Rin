## 第三轮：拔掉测试里对真实 S3 网络的依赖（同日，commit dddce89）

用户说「改」，按上一轮报告里点名要改的两处测试基础设施缺陷执行。

### 1）mock env 的 S3 端点指向真实 R2（这才是 4 个 rss 抖动失败的根因）
`tests/fixtures/index.ts` 里 `S3_ENDPOINT: 'https://test.r2.cloudflarestorage.com'` ——
这域名**真实可解析**，未被 `fetch` 打桩的用例会真的发请求并等网络失败。
实测（真实 `S3Client` + `getObject`）：旧配置 1389 ms，新配置 87 ms。
基线 `rss.test.ts` 单文件 **29.96 s / 1 fail**（11 个 GET 用例各等约 2.7 s）。
改法：`S3_ENDPOINT: 'http://127.0.0.1:9'` + `S3_FORCE_PATH_STYLE: 'true'`。
**为什么必须同时开 path style**：虚拟主机风格会把桶名拼进主机名（`test-bucket.127.0.0.1`），
那样又要靠 DNS 快速失败——本机 DNS 对不可路由名的响应很不稳定
（实测 `test.r2.invalid` 要 4347 ms，`test-bucket.127.0.0.1` 108 ms，纯属碰运气）。
path style 让请求目标就是裸 IP，**完全不查 DNS**。已加注释警告别改回去。
`cache.test.ts` 里那份重复的 mock env 同步改掉。
结果：`rss.test.ts` 11.47 s / 0 fail；全量 33.07 s → 27.1~28.3 s。

### 2）最后一处 `mock.module` 泄漏
`fetch-handler.test.ts` 用 `mock.module("../app-instance", ...)` 整块替换命名空间。
按上一轮实测的 Bun 语义，这会泄漏给后续文件。修法与 `handleScheduled` 一致：
`handleFetch(request, env, resolveApp = getApp)` 增加可选第 3 参。
`_worker.ts` 是显式 `handleFetch(request, env)` 调用（不是把函数本身挂成 handler），
所以加可选参会把 `ctx` 误当注入参数的风险不存在。
`favicon.test.ts` 里拦截用的对象 URL 改为由 mock env 推导，端点再变不会静默失配。
反向验证：把 `resolveApp()` 换回 `getApp()` → 2 个用例精确失败。✅
