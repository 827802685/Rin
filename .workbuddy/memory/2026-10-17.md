### 修的两个真 bug

① **一条坏消息饿死整批**（`queue-handler.ts`）：`for` 循环里 `FEED_AI_SUMMARY_TASK`

   任何抛出（D1 抖动、`getAIConfig` 失败）→ `handleQueue` reject → 它后面的消息

   而 `syncFeedAISummaryQueueState` 只在文章真更新时才重新入队 ⇒ 再也要不到摘要。

（与正常失败路径一致，后台「重试」能捞回来）。

### 经验（供后续复用）

① **给「处理器注入」找范式直接抄 `scheduled-handler.ts`**：它已经有
   `ScheduledTaskModules` + `loadScheduledTaskModules()` 动态 import 的写法，
   `queue-handler.ts` 照搬成 `QueueTaskModules` 即可，不用新发明，也绕开
   bun `mock.module` 跨文件残留。
② **验证「某段代码抛出后 DB 行是什么状态」必须能注入那个抛出点**。
   直接给被测函数加一个**带默认值的可选尾参**（如
   `generateSummary: typeof generateAISummaryResult = generateAISummaryResult`）
   比任何 mock 都干净：生产行为零变化，测试里传个 throw 即可。
   这比「让 serverConfig.get 第二次调用才抛」那种计数式假环境可靠得多。
③ **变异「去掉 try/catch」别留悬空 `}`**：把
   `try { ... } catch (e) { ... }` 整体换成 `{ ... }`（块语句），语法合法，
   不会像删行那样制造整文件语法错误 → 假红。
④ **判「是既有失败还是回归」时先 fetch**：本轮 `git fetch origin main` 一次就通，
   别默认网络不通（10-16 那轮是 21 秒连不上，属于偶发）。
